# Автоматическая генерация признаков для ранжирования в рекомендациях (KION)

Можно ли заменить ручные агрегатные признаки для градиентного бустинга признаками, которые порождаются автоматически из небольшой грамматики и отбираются по валидации? И правда ли нужно выбирать «окно 7 дней» руками?

## Кратко

- Построен воспроизводимый двухэтапный пайплайн на KION: кандидаты (популярность + item-to-item), затем градиентный бустинг. Разбиение строго по времени, утечки проверяются в коде.
- Автоматический генератор признаков из грамматики «связь × временное ядро × мера × нормировка» (288 признаков, без ручного выбора окон) **сравнялся с ручным набором**: NDCG@10 на тесте 0.1530 против 0.1514, разница +0.0016, 95% CI [−0.0007, +0.0038].
- Ручные и сгенерированные признаки вместе дают **небольшой значимый прирост**: 0.1543, +0.0029 [+0.0011, +0.0050]. Главный новый сигнал — очень свежая (полупериод 1 день) популярность внутри демографической группы.
- На вопрос «почему 7 дней» ответ такой: устойчиво лучшего окна нет, ранги ядер меняются между валидацией и тестом. Набор из нескольких масштабов экспоненциального затухания сразу достигает уровня ручного набора.
- Отбор признаков по permutation importance сжимает набор (93 признака вместо 301, обучение в 4 раза быстрее), но качество не улучшает.

## 1. Задача и данные

**Датасет:** KION от МТС ([репозиторий датасета](https://github.com/irsafilo/KION_DATASET), версия `data_original`). Это просмотры фильмов и сериалов с 13.03.2021 по 22.08.2021: `user_id, item_id, last_watch_dt, total_dur, watched_pct`, плюс признаки пользователей (возраст, доход, пол, наличие детей) и фильмов (тип, жанры, год, возрастной рейтинг и т.д.).

**Сэмпл:** 200 000 случайных пользователей (seed 42), у каждого сохранена вся история, как требует условие. Это около 1,14 млн взаимодействий.

**Задача:** для пользователя, который уже что-то смотрел, предсказать, какие *новые для него* объекты он посмотрит на следующей неделе. Положительная пара (user, item) — объект, у которого `last_watch_dt` попадает в целевую неделю. Метрики: Recall@10, NDCG@10, MAP@10 по всем тёплым пользователям, активным в целевой неделе. Знаменатель — все их целевые объекты, включая те, что не попали в кандидаты. Дополнительно указан ROC-AUC на парах-кандидатах.

Особенность KION: в таблице одна строка на пару (user, item) с датой *последнего* просмотра. Поэтому пара, досмотренная в целевой неделе, целиком отсутствует в истории. Это не утечка: признаки строятся только по строкам с датой строго раньше отсечки, а начатые и не законченные до отсечки просмотры модель просто не видит.

## 2. Протокол эксперимента

### Разбиение по времени

| Выборка | История для признаков | Целевая неделя | Для чего |
|---|---|---|---|
| train | до 2021-08-02 | 2021-08-02 – 08-08 | обучение бустинга |
| val | до 2021-08-09 | 2021-08-09 – 08-15 | отбор признаков, выбор k |
| test | до 2021-08-16 | 2021-08-16 – 08-22 | итоговая оценка |

Для каждой выборки признаки пересчитываются заново по истории до её отсечки. Тестовая неделя ни разу не используется для выбора чего бы то ни было.

**Защита от утечек** (проверяется `assert` в коде):
- в истории для признаков нет ни одной строки с датой ≥ даты отсечки;
- ни одна пара-кандидат не встречается в истории, то есть кандидаты — только новые для пользователя объекты, а целевое событие не может попасть в признаки;
- метрики на val и test считаются по фиксированной выборке из 8 000 пользователей; одни и те же кандидаты и пользователи используются для всех моделей.

### Двухэтапная схема

1. **Кандидаты** (одинаковые для всех моделей): 50 самых популярных объектов за 7 дней до отсечки и 50 объектов, ближайших к последним 10 просмотрам пользователя по косинусной мере совместных просмотров (item-to-item). Уже просмотренное убирается. В среднем около 84 кандидатов на пользователя.
2. **Ранжирование:** `HistGradientBoostingClassifier` из scikit-learn с одинаковыми гиперпараметрами для всех моделей (300 итераций, learning rate 0.05, 63 листа, `min_samples_leaf=50`, L2 = 1). Обучение — на всех положительных парах и 20 случайных отрицательных на пользователя (только пользователи, у которых есть хотя бы один положительный кандидат).

Гиперпараметры бустинга одни и те же для всех вариантов и не подбирались, чтобы сравнение было только по признакам.

### Что получает каждая модель

- **base** (13 признаков, есть у всех GBDT): скоры первого этапа (`pop_rank`, `i2i_score`, `i2i_rank`) и статические атрибуты пользователя и объекта (возраст, доход, пол, дети, тип, год выпуска, десятилетие, для детей, возрастной рейтинг, число жанров).
- **ручные агрегаты** (20 признаков): число просмотров пользователя за 7, 30 дней и за всё время, средний `watched_pct`, длительность за 30 дней, дни с первого и последнего просмотра, доля сериалов; популярность объекта за 7, 30 дней, всё время и предыдущую неделю, тренд, средний `watched_pct`, средняя длительность, возраст объекта в данных; доля жанров объекта в истории пользователя (max и mean), совпадение типа контента, популярность объекта в возрастной группе пользователя за 30 дней.

## 3. Исследовательская идея: грамматика признаков

Большинство ручных признаков — это агрегаты вида
`SELECT agg(weight · measure) FROM events WHERE time < cut GROUP BY <связь>`.
Мы задаём пространство таких запросов явно и перебираем его автоматически.

| Измерение | Значения |
|---|---|
| Связь (relation) | `user`, `item`; косвенные связи пользователя: `user×genre`, `user×content_type`, `user×decade`; объект в группе пользователей: `item×age`, `item×income`, `item×sex`, `item×kids` |
| Временное ядро | экспоненциальное затухание `w = 0.5^(d/h)` с полупериодом h ∈ {1, 3, 7, 14, 30, 90} дней; жёсткие окна 7 и 30 дней; вся история |
| Мера | взвешенное число событий; взвешенная «досмотренность» Σ w·watched_pct/100 |
| Нормировка | как есть; доля от родителя в том же ядре (например, доля жанра в истории пользователя или доля объекта в просмотрах возрастной группы) |

Для многозначной связи (у фильма несколько жанров) значение агрегируется по жанрам объекта через max. Всего получается 288 признаков. Генератор занимает около 100 строк (`auto_features` в `pipeline.py`) и считает все признаки за десятки секунд.

**Почему затухание вместо окон.** Жёсткое окно «7 дней» отбрасывает событие 8-дневной давности целиком, а затухание учитывает его с меньшим весом. Полупериод — непрерывный параметр, его можно выбрать по валидации так же, как любой гиперпараметр, вместо того чтобы фиксировать вручную.

**Отбор:** бустинг обучается на base + все 288 признаков. Затем на валидации считается permutation importance: падение ROC-AUC при перемешивании одного признака, на 40 000 валидационных строк — все положительные плюс случайные отрицательные. Берутся top-k для k ∈ {10, 20, 40, 80}, и k выбирается по NDCG@10 на валидации. Тест в отборе не участвует.

**Исследование окон:** фиксируем 5 связей (`user`, `item`, `user×genre`, `user×content_type`, `item×age`) и меняем только временное ядро. Каждая модель получает base + 5 признаков.

## 5. Анализ

**1. Ручные агрегаты дают основной прирост.** Модель только на base (скоры кандидатов и статические атрибуты) почти не обходит популярность: NDCG@10 на тесте 0.1358 против 0.1323. Ручные агрегаты поднимают метрику до 0.1514, то есть на +0.0156 [+0.0129, +0.0183]. Именно с этим уровнем сравнивается автоматика.

**2. Сгенерированные признаки догоняют ручные без ручного выбора.** Бустинг на base + все 288 сгенерированных признаков даёт 0.1530: разность +0.0016 с 95% CI [−0.0007, +0.0038], то есть статистически неотличимо от ручного набора. При равном числе признаков (33: base + top-20 сгенерированных) получается 0.1513 против 0.1514. Грамматика из 4 измерений и автоматический отбор воспроизводят качество, которое в базовой модели достигнуто вручную подобранными признаками.

**3. Вместе лучше, чем по отдельности.** Ручные + top-80 сгенерированных дают 0.1543, +0.0029 [+0.0011, +0.0050] к ручным — небольшой, но статистически значимый прирост. Значит, грамматика находит сигнал, которого нет в ручном наборе. Судя по permutation importance, это прежде всего **очень свежая популярность внутри демографической группы**: самый важный признак — `item_sex|exp1|cnt|share` (доля объекта в просмотрах пользователей того же пола с затуханием за 1 день). В ручном наборе есть популярность за 7 и 30 дней и популярность в возрастной группе за 30 дней, но нет сочетания «группа × очень короткий масштаб».

**4. Отбор по важности сжимает, но не улучшает.** На валидации кривая по k почти плоская начиная с k = 40 (0.1570 при k = 40 и 0.1573 при k = 80), выбрано k = 80. На тесте top-80 даёт 0.1505, что не лучше полного набора (0.1530) и в пределах шума относительно ручного. Польза отбора — в стоимости: обучение на 93 признаках занимает 22 с против 88 с на 301 признаке. Слабое место метода: важность считается по ROC-AUC (поточечно), а не по NDCG, и коррелированные признаки (одна связь с соседними полупериодами) делят важность между собой.

**5. «Почему именно 7 дней?» — одного правильного окна нет.** В исследовании окон (те же 5 связей, меняется только ядро) все варианты на тесте лежат в узком диапазоне 0.1432–0.1495. Порядок ядер не воспроизводится между валидацией и тестом: лучшее на валидации — затухание с полупериодом 90 дней (0.1530), лучшее на тесте — 30 дней (0.1495). Жёсткое окно 7 дней на тесте худшее (0.1432), но на валидации оно седьмое из девяти: два ядра там хуже него. Поэтому мы не утверждаем, что какой-то полупериод лучше. Устойчивый вывод другой: если дать модели **все масштабы затухания сразу** (43 признака), она достигает 0.1517, то есть уровня ручного набора (+0.0003 [−0.0018, +0.0024]), а одно любое ядро отстаёт от него на 0.002–0.008. По суммарной важности выигрывают крайние масштабы: затухание за 1 день (0.0233) и вся история (0.0124). Модель комбинирует «что популярно прямо сейчас» и «что популярно вообще», и вместо выбора окна достаточно дать ей несколько масштабов.

**6. Цена автоматизации.** Генерация 288 признаков занимает 13–22 с на выборку против 2–3 с для ручных (около 8 раз дольше), обучение на полном наборе — 88 с против 10 с, отбор — 287 с. Для 200 тыс. пользователей это минуты. Каждый признак грамматики — это `GROUP BY` с взвешенной суммой, поэтому генератор прямо переводится в SQL, и на промышленных объёмах стоимость линейна по числу событий × число ядер × число связей. Узкое место масштабирования — не генерация, а отбор: permutation importance требует одного прогноза на признак.

**Что не сработало.** Отбор top-k не дал выигрыша над полным набором. Ни одно отдельное временное ядро не стало устойчиво лучшим. Item-to-item кандидаты сами по себе слабее популярности (0.1145 против 0.1323), их ценность проявляется только как признак ранжировщика.

## 6. Ограничения

- **Один датасет и один сэмпл.** 200 тыс. пользователей с одним seed. Доверительные интервалы учитывают только разброс по тестовым пользователям, но не случайность сэмпла, отрицательных примеров и обучения. Различия порядка 0.002 NDCG нужно проверять на нескольких сэмплах и на полном датасете.
- **Потолок из-за кандидатов:** recall кандидатов около 0.37, поэтому любой ранжировщик ограничен сверху. Сравнение моделей корректно (кандидаты общие), но абсолютные значения метрик низкие.
- **Только тёплые пользователи** с историей до отсечки. Холодные пользователи не оцениваются.
- **Гиперпараметры бустинга фиксированы и не подбирались.** Модель поточечная (классификация с семплированием отрицательных), а не LambdaRank; использован HistGradientBoosting из scikit-learn, а не LightGBM или CatBoost.
- **Грамматика ограничена:** нет текстовых признаков (описания, ключевые слова), актёров и режиссёров, item-item связей помимо скора первого этапа, отношений признаков (конверсий) и пересечений из трёх и более сущностей.
- **Особенность KION:** одна строка на пару (user, item) с датой последнего просмотра. Просмотры, начатые до отсечки и законченные после, не видны в истории.
- **Отбор признаков по ROC-AUC,** а не по целевой метрике NDCG. Перебор подмножеств (forward selection, поиск с ИИ-агентом) не исследован.

## 7. Воспроизведение

```bash
git clone https://github.com/irsafilo/KION_DATASET
unzip KION_DATASET/data_original.zip -d .          # даёт data_original/{interactions,users,items}.csv
pip install -r requirements.txt
python pipeline.py --data data_original --out results   # около 15 минут на 2 ядрах CPU, хватает 7 ГБ ОЗУ
python make_tables.py results/results.json               # таблицы из раздела 4
```

Все числа в README взяты из `results/results.json`, сгенерированного этим кодом. Таблицы строит `make_tables.py`, вручную не набирались. Время в таблицах замерено на 2 ядрах CPU.
