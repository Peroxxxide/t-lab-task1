# Автоматическая генерация признаков для ранжирования в рекомендациях (KION)

Можно ли заменить ручные агрегатные признаки для градиентного бустинга признаками, которые порождаются автоматически из небольшой грамматики и отбираются по валидации? И правда ли нужно выбирать «окно 7 дней» руками?

## Кратко: основные выводы

- Построен воспроизводимый двухэтапный пайплайн на KION: кандидаты (популярность + item-to-item), затем градиентный бустинг. Разбиение строго по времени, утечки проверяются в коде.
- Автоматический генератор признаков из грамматики «связь × временное ядро × мера × нормировка» (288 признаков, без ручного выбора окон) **сравнялся с ручным набором**: NDCG@10 на тесте 0.1530 против 0.1514, разница +0.0016, 95% CI [-0.0007, +0.0038].
- Ручные и сгенерированные признаки вместе дают **небольшой значимый прирост**: 0.1543, +0.0029 [+0.0011, +0.0050]. Наиболее вероятный источник прироста - очень свежая (полупериод 1 день) популярность внутри демографической группы.
- На вопрос «почему 7 дней» ответ такой: устойчиво лучшего окна нет, ранги ядер меняются между валидацией и тестом. Набор из нескольких масштабов экспоненциального затухания сразу достигает уровня ручного набора.
- Отбор признаков по permutation importance сжимает набор (93 признака вместо 301, обучение в 4 раза быстрее), но качество не улучшает.
- Выводы проверены на второй машине и на LightGBM: во всех трёх прогонах сгенерированные признаки на уровне ручных, а их объединение даёт значимый прирост (+0.0026...+0.0041 NDCG@10).

## 1. Задача и данные

**Датасет:** KION от МТС ([репозиторий датасета](https://github.com/irsafilo/KION_DATASET), версия `data_original`). Это просмотры фильмов и сериалов с 13.03.2021 по 22.08.2021: `user_id, item_id, last_watch_dt, total_dur, watched_pct`, плюс признаки пользователей (возраст, доход, пол, наличие детей) и фильмов (тип, жанры, год, возрастной рейтинг и т.д.). Датасет описан в работе: A. Petrov, I. Safilo, D. Tikhonovich, D. Ignatov. *MTS Kion Implicit Contextualised Sequential Dataset for Movie Recommendation*. ACM RecSys CARS Workshop, 2022 (авторы просят ссылаться на неё в README репозитория датасета).

**Сэмпл:** 200 000 случайных пользователей (seed 42), у каждого сохранена вся история, как требует условие. Это 1 136 447 взаимодействий.

**Задача:** для пользователя, который уже что-то смотрел, предсказать, какие *новые для него* объекты он посмотрит на следующей неделе. Положительная пара (user, item) - объект, у которого `last_watch_dt` попадает в целевую неделю. Метрики: Recall@10, NDCG@10, MAP@10 по всем тёплым пользователям, активным в целевой неделе. Знаменатель - все их целевые объекты, включая те, что не попали в кандидаты. Дополнительно указан ROC-AUC на парах-кандидатах. MAP@10 добавлен потому, что по нему оценивались решения соревнования Kion Challenge, для которого использовался этот датасет (см. README репозитория датасета). LogLoss не приводится: бустинг обучается на выборке с семплированием отрицательных примеров (20 на пользователя), поэтому его вероятности сдвинуты относительно реальной доли положительных, и LogLoss отражал бы эту калибровку, а не качество ранжирования. Для сравнения моделей при общем наборе кандидатов важен порядок, а не абсолютные вероятности, поэтому основная метрика - NDCG@10.

Особенность KION: в таблице одна строка на пару (user, item) с датой *последнего* просмотра. Поэтому пара, последний просмотр которой пришёлся на целевую неделю, целиком отсутствует в истории. Это не утечка: признаки строятся только по строкам с датой строго раньше отсечки. Обратная сторона - если пользователь начал смотреть объект (например, сериал) до отсечки, а последний раз смотрел его в целевую неделю, то в истории этого просмотра нет, и объект выглядит для модели новым. По той же причине повторные просмотры в данных не наблюдаются, поэтому рекомендуются только новые для пользователя объекты. Прямые признаки пары вида «сколько раз пользователь смотрел этот объект» для таких кандидатов всегда равны нулю и не используются. Связь пользователя с объектом описывается косвенно: через жанр, тип контента, десятилетие и демографическую группу, а также через item-to-item скор первого этапа.

## 2. Протокол эксперимента

### Разбиение по времени

| Выборка | История для признаков | Целевая неделя | Для чего |
|---|---|---|---|
| train | до 2021-08-02 | 2021-08-02 - 08-08 | обучение бустинга |
| val | до 2021-08-09 | 2021-08-09 - 08-15 | отбор признаков, выбор k |
| test | до 2021-08-16 | 2021-08-16 - 08-22 | итоговая оценка |

Для каждой выборки признаки пересчитываются заново по истории до её отсечки. Тестовая неделя ни разу не используется для выбора чего бы то ни было.

**Защита от утечек** (проверяется `assert` в коде):
- в истории для признаков нет ни одной строки с датой ≥ даты отсечки;
- ни одна пара-кандидат не встречается в истории, то есть кандидаты - только новые для пользователя объекты, а целевое событие не может попасть в признаки.

**Единый протокол сравнения:** метрики на val и test считаются по фиксированной случайной выборке из 8 000 тёплых пользователей, активных в соответствующей целевой неделе (seed 42); одни и те же пользователи, кандидаты и гиперпараметры используются для всех моделей.

**Оговорка о ходе работы:** после первого полного прогона протокол был изменён один раз - базовые признаки (скоры кандидатов и статические атрибуты) добавлены ко всем моделям со сгенерированными признаками. Без них сравнение было нечестным: ручной набор эти признаки содержал, а сгенерированный нет. Других изменений постановки после просмотра результатов не было.

### Двухэтапная схема

1. **Кандидаты** (одинаковые для всех моделей): 50 самых популярных объектов за 7 дней до отсечки (по числу просмотревших пользователей сэмпла) и 50 объектов, ближайших к последним 10 просмотрам пользователя по косинусной мере совместных просмотров (item-to-item). Уже просмотренное убирается. В среднем около 84 кандидатов на пользователя.
2. **Ранжирование:** `HistGradientBoostingClassifier` из scikit-learn с одинаковыми гиперпараметрами для всех моделей (300 итераций, learning rate 0.05, до 63 листьев в дереве, `min_samples_leaf=50`, L2 = 1, без ранней остановки). Обучение - только на train-неделе: все положительные пары среди кандидатов и 20 случайных отрицательных на пользователя (только пользователи, у которых есть хотя бы один положительный кандидат).

Гиперпараметры бустинга одни и те же для всех вариантов и не подбирались, чтобы сравнение было только по признакам.

### Что получает каждая модель

- **base** (13 признаков, есть у всех GBDT): скоры первого этапа (`pop_rank`, `i2i_score`, `i2i_rank`) и статические атрибуты пользователя и объекта (возраст, доход, пол, дети, тип, год выпуска, десятилетие, для детей, возрастной рейтинг, число жанров). Атрибуты берутся из справочников датасета как есть, то есть это снимок на момент выгрузки, а не на дату отсечки.
- **ручные агрегаты** (20 признаков, все по истории до отсечки):
  - пользователь (8): число просмотров за 7 и 30 дней и за всё время; средний `watched_pct`; логарифм суммарной длительности просмотров за 30 дней; дни с первого и с последнего просмотра; доля сериалов в истории;
  - объект (8): число просмотров за 7 и 30 дней, за всё время и за предыдущую неделю (8-14 дней до отсечки); тренд (просмотры за 7 дней + 1) / (за предыдущую неделю + 1); средний `watched_pct`; логарифм средней длительности просмотра; дни с первого просмотра объекта в данных;
  - пара (4): доля жанров объекта в истории пользователя (max и mean по жанрам объекта); доля объектов того же типа (фильм или сериал) в истории пользователя; доля объекта в просмотрах пользователей той же возрастной группы за 30 дней.

## 3. Исследовательская идея: грамматика признаков

Большинство ручных признаков - это агрегаты вида
`SELECT agg(weight · measure) FROM events WHERE time < cut GROUP BY <связь>`.
Мы задаём пространство таких запросов явно и перебираем его автоматически.

| Измерение | Значения |
|---|---|
| Связь (relation) | `user`, `item`; косвенные связи пользователя: `user×genre`, `user×content_type`, `user×decade`; объект в группе пользователей: `item×age`, `item×income`, `item×sex`, `item×kids` |
| Временное ядро | экспоненциальное затухание `w = 0.5^(d/h)`, где d - число дней от просмотра до отсечки (d ≥ 1), с полупериодом h ∈ {1, 3, 7, 14, 30, 90} дней; жёсткие окна 7 и 30 дней; вся история |
| Мера | взвешенное число событий; взвешенная «досмотренность» Σ w·watched_pct/100 |
| Нормировка | как есть; доля от родителя в том же ядре (например, доля жанра в истории пользователя или доля объекта в просмотрах возрастной группы). Доля есть только у связей-пар; у `user` и `item` - только «как есть» |

Для многозначной связи (у фильма несколько жанров) значение агрегируется по жанрам объекта через max. Всего получается 2 связи × 9 ядер × 2 меры + 7 связей × 9 ядер × 2 меры × 2 нормировки = 36 + 252 = 288 признаков. Генератор занимает около 100 строк (`auto_features` в `pipeline.py`) и считает все признаки за десятки секунд.

**Почему затухание вместо окон.** Жёсткое окно «7 дней» отбрасывает событие 8-дневной давности целиком, а затухание учитывает его с меньшим весом. Полупериод - непрерывный параметр, его можно выбирать по валидации, как гиперпараметр, или дать модели сразу несколько масштабов. В результатах ниже устойчиво лучшего полупериода не нашлось, а набор из нескольких масштабов сработал лучше любого одного.

**Отбор:** бустинг обучается на base + все 288 признаков. Затем на валидации считается permutation importance: падение ROC-AUC при перемешивании одного сгенерированного признака (base не перемешивается), на 40 000 валидационных строк - все положительные плюс случайные отрицательные. Берутся top-k для k ∈ {10, 20, 40, 80}, и k выбирается по NDCG@10 на валидации. Тест в отборе не участвует. Валидация используется дважды (для важности и для выбора k), поэтому качество на ней для отобранных наборов слегка оптимистично; итоговое сравнение - только по тесту.

**Исследование окон:** фиксируем 5 признаков - число событий для `user` и `item` (как есть) и доли для `user×genre`, `user×content_type`, `item×age` - и меняем только временное ядро. Каждая модель получает base + 5 признаков. Вариант «все затухания вместе» - те же 5 признаков для всех 6 полупериодов (30 признаков).

## 5. Анализ

**1. Ручные агрегаты дают основной прирост.** Модель только на base (скоры кандидатов и статические атрибуты) почти не обходит популярность: NDCG@10 на тесте 0.1358 против 0.1323. Ручные агрегаты поднимают метрику до 0.1514, то есть на +0.0156 [+0.0129, +0.0183]. Именно с этим уровнем сравнивается автоматика.

**2. Сгенерированные признаки догоняют ручные без ручного выбора.** Бустинг на base + все 288 сгенерированных признаков даёт 0.1530: разность +0.0016 с 95% CI [-0.0007, +0.0038], то есть статистически неотличимо от ручного набора. При равном числе признаков (33: base + top-20 сгенерированных) получается 0.1513 против 0.1514. Грамматика из 4 измерений воспроизводит качество, которого в эталонной модели добились вручную подобранными признаками. Это повторилось на второй машине (-0.0001) и на LightGBM (-0.0005).

**3. Вместе лучше, чем по отдельности.** Ручные + top-80 сгенерированных дают 0.1543, +0.0029 [+0.0011, +0.0050] к ручным - небольшой, но статистически значимый прирост; он повторился на второй машине (+0.0026) и на LightGBM (+0.0041). Значит, грамматика находит сигнал, которого нет в ручном наборе. Какой именно, мы напрямую не измеряли: важность считалась в модели без ручных признаков. Наиболее вероятный кандидат - **очень свежая популярность внутри демографической группы**: самый важный сгенерированный признак - `item_sex|exp1|cnt|share` (доля объекта в просмотрах пользователей того же пола с затуханием за 1 день). В ручном наборе есть популярность за 7 и 30 дней и популярность в возрастной группе за 30 дней, но нет сочетания «группа × очень короткий масштаб».

**4. Отбор по важности сжимает, но не улучшает.** На валидации кривая по k почти плоская начиная с k = 40 (0.1570 при k = 40 и 0.1573 при k = 80), выбрано k = 80. На тесте top-80 даёт 0.1505, что не лучше полного набора (0.1530) и в пределах шума относительно ручного. Польза отбора - в стоимости: обучение на 93 признаках занимает 22 с против 88 с на 301 признаке. Слабое место метода: важность считается по ROC-AUC (поточечно), а не по NDCG, и коррелированные признаки (одна связь с соседними полупериодами) делят важность между собой.

**5. «Почему именно 7 дней?» - одного правильного окна нет.** В исследовании окон (те же 5 признаков, меняется только ядро) все варианты на тесте лежат в узком диапазоне 0.1432-0.1495. Порядок ядер не воспроизводится между валидацией и тестом: лучшее на валидации - затухание с полупериодом 90 дней (0.1530), лучшее на тесте - 30 дней (0.1495). Жёсткое окно 7 дней на тесте худшее (0.1432), но на валидации оно седьмое из девяти: два ядра там хуже него. Поэтому мы не утверждаем, что какой-то полупериод лучше. Устойчивый вывод другой: если дать модели **все масштабы затухания сразу** (43 признака), она достигает 0.1517, то есть уровня ручного набора (+0.0003 [-0.0018, +0.0024]; на второй машине и на LightGBM - даже значимо выше, +0.0030 и +0.0027), а одно любое ядро отстаёт от него на 0.002-0.008. По суммарной важности выигрывают крайние масштабы: затухание за 1 день (0.0233) и вся история (0.0124). По-видимому, модель комбинирует «что популярно прямо сейчас» и «что популярно вообще», и вместо выбора окна достаточно дать ей несколько масштабов.

**6. Цена автоматизации.** Генерация 288 признаков занимает 13-22 с на выборку против 2-3 с для ручных (около 8 раз дольше), обучение на полном наборе - 88 с против 10 с, отбор - 287 с. Для 200 тыс. пользователей это минуты. Каждый признак грамматики - это `GROUP BY` с взвешенной суммой, поэтому генератор прямо переводится в SQL, и на промышленных объёмах стоимость растёт примерно линейно по числу событий × число ядер × число связей (для жанров события размножаются по числу жанров объекта). Узкое место масштабирования - не генерация, а отбор: permutation importance требует одного прогноза на признак.

**Что не сработало.** Отбор top-k не дал выигрыша над полным набором. Ни одно отдельное временное ядро не стало устойчиво лучшим. Ранжирование сначала по item-to-item само по себе слабее популярности (0.1145 против 0.1323). Вклад item-to-item как источника кандидатов и как признака ранжировщика отдельно не проверялся.

## 6. Ограничения

- **Один датасет, один сэмпл, один период.** 200 тыс. пользователей с одним seed, три соседние недели августа 2021. Доверительные интервалы учитывают только разброс по тестовым пользователям, но не случайность сэмпла, отрицательных примеров и обучения. Повтор на другой машине показал, что сама реализация даёт разброс до 0.0023 NDCG@10, поэтому различия такого порядка нужно проверять на нескольких сэмплах, периодах и на полном датасете.
- **Потолок из-за кандидатов:** recall кандидатов около 0.37, поэтому любой ранжировщик ограничен сверху. Сравнение моделей корректно (кандидаты общие), но абсолютные значения метрик низкие.
- **Только тёплые пользователи** с историей до отсечки. Холодные пользователи не оцениваются.
- **Гиперпараметры бустинга фиксированы и не подбирались.** Модель поточечная (классификация с семплированием отрицательных), а не LambdaRank; основной прогон сделан на HistGradientBoosting из scikit-learn (гистограммный градиентный бустинг; в документации scikit-learn сказано, что реализация вдохновлена LightGBM). Повтор на LightGBM с теми же настройками дал те же выводы (раздел «Проверка на LightGBM»). Подбор гиперпараметров для каждого набора признаков и проверка на CatBoost - следующий шаг: подбор может усилить ручной и сгенерированный наборы по-разному.
- **Грамматика ограничена:** нет текстовых признаков (описания, ключевые слова), актёров и режиссёров, item-item связей помимо скора первого этапа, отношений признаков (конверсий) и пересечений из трёх и более сущностей.
- **Особенность KION:** одна строка на пару (user, item) с датой последнего просмотра. Если объект начали смотреть до отсечки, а последний раз смотрели после, в истории его нет, и он выглядит новым (особенно касается сериалов). Повторные просмотры не наблюдаются.
- **Статические атрибуты** пользователей и объектов - снимок на момент выгрузки датасета, а не на дату отсечки; исторических значений в датасете нет. Для объектов атрибуты (год, тип, жанры, рейтинг) не меняются; для пользователей группы широкие, а период - около 5 месяцев. Атрибуты входят в base и одинаковы у всех сравниваемых моделей.
- **Отбор признаков по ROC-AUC,** а не по целевой метрике NDCG. Перебор подмножеств (forward selection, поиск с ИИ-агентом) не исследован.

## 7. Воспроизведение

```bash
git clone https://github.com/irsafilo/KION_DATASET
unzip KION_DATASET/data_original.zip -d .          # даёт data_original/{interactions,users,items}.csv
pip install -r requirements.txt
python pipeline.py --data data_original --out results   # около 15 минут на 2 ядрах CPU, хватает 7 ГБ ОЗУ
python make_tables.py results/results.json               # таблицы из раздела 4

# проверка на LightGBM (нужен pip install lightgbm)
python pipeline.py --data data_original --out results_lgbm --model lgbm
```

На Windows архив можно распаковать вручную, а вместо `python` может понадобиться `py`. Проверенные версии библиотек указаны в таблице раздела «Повтор на второй машине». Файлы `results/results_second_machine.json` и `results/results_lightgbm.json` получены на второй машине первой и последней командами соответственно.

Повторный запуск с теми же параметрами на той же машине дал идентичный `results.json` (отличаются только замеры времени); на другой машине числа расходятся до 0.0023 NDCG@10 на тесте, см. «Повтор на второй машине». Числа основного прогона взяты из `results/results.json`, сгенерированного этим кодом; таблицы раздела 4 строит `make_tables.py`, вручную они не набирались. Числа в таблицах «Повтор на второй машине» и «Проверка на LightGBM» перенесены из вывода этих прогонов; те же значения сохранены в `results/results_second_machine.json` и `results/results_lightgbm.json`. Время в таблицах замерено в основном прогоне (2 ядра CPU).
